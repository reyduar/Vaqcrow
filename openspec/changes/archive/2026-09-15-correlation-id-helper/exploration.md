## Exploration: Correlation ID Helper (`correlation-id-helper`, issue #116)

### Current State

- `packages/contracts` is still a placeholder. Its public barrel exports only `WorkspaceProbe` and `describeWorkspace`; its tests cover only that probe, and its manifest has no runtime dependency.
- `apps/api` is a minimal Fastify 5.12.4 application. `buildApp()` creates the server with logging disabled and registers only `GET /health`; no hook, request decoration, response header, event payload, or correlation-ID behavior exists.
- The API application layer already consumes `@vaqcrow/contracts`, while Fastify remains in `src/infrastructure/http`. Dependency Cruiser rejects runtime Fastify/provider imports from `apps/api/src/application/`, but there is no equivalent rule protecting `packages/contracts` from framework/provider imports.
- Vitest is configured per workspace, and the root `verify` command runs lint, typecheck, tests, build, dependency boundaries, and boundary tests. Strict TypeScript settings include `NodeNext`, `isolatedModules`, and `verbatimModuleSyntax`.
- Issue #38 and parent feature #12 remain open, with no branch, pull request, comment, dependency, or library decision in the inspected repository. No validation library is a direct dependency. Zod 4.6.5 appears only transitively through `eslint-plugin-react-hooks`, so it cannot be treated as an application dependency.
- The architecture allows `apps/api` to depend on contracts and assigns API/event/adapter schemas to `packages/contracts`. It prohibits framework/provider leakage into domain/application concerns. `apps/web` also depends on the contracts package, so a static Node-only import in the root contracts barrel would create an avoidable portability risk.
- Fastify already assigns `request.id` before request hooks. Its documented `requestIdHeader` option performs no validation and lets callers choose arbitrary IDs; `genReqId` is expected to be error-free. Therefore, directly enabling an inbound correlation header would bypass the required parser unless extra infrastructure policy is added.
- The authoritative store is OpenSpec, but `openspec/` and `openspec/config.yaml` were absent at inspection time. This exploration creates only the required change artifact; native `sdd-new` still needs to establish the normal change state/configuration expected by later phases.

### Affected Areas

- `packages/contracts/package.json` — add the selected runtime validator as a direct production dependency; keep tooling dependencies separate.
- `packages/contracts/src/correlation-id.ts` — natural home for the schema, opaque type, parser, and generator.
- `packages/contracts/src/index.ts` — expose the new contract through the package's existing public entry point.
- `packages/contracts/src/index.test.ts` or `packages/contracts/src/correlation-id.test.ts` — cover generation, successful parsing, malformed-input rejection, and type-oriented usage where practical.
- `apps/api/src/infrastructure/http/build-app.ts` — exact HTTP composition point for Fastify request-ID generation and response propagation.
- `apps/api/src/infrastructure/http/build-app.test.ts` — prove a request receives a valid correlation ID and the response exposes the same value.
- `.dependency-cruiser.cjs` and `tests/boundaries.test.ts` — optionally make the contracts framework/provider-free requirement executable while still allowing the validator.
- `pnpm-workspace.yaml` and `pnpm-lock.yaml` — record the direct validator dependency consistently; a catalog entry would let #38 reuse the same version.

### Open Decisions

1. **Identifier format** — UUID v4, UUID v7, ULID, or a bounded opaque string are all possible. The issue does not define ordering, encoding, or interoperability requirements.
   - Recommendation: canonical UUID v4 generated by Web Crypto `randomUUID()`. It is available in the declared Node 24 runtime, avoids another ID-generation package, and Zod 4 has a dedicated UUID-v4 validator.
   - Constraint: avoid a static `node:crypto` import from the root contracts entry point unless browser compatibility is intentionally abandoned; `apps/web` is already a consumer.
2. **Runtime validator** — #38 has not selected one.
   - Recommendation: add Zod 4 as a direct `packages/contracts` dependency and workspace catalog entry, then have #38 reuse it. A branded `z.uuidv4()` schema can provide runtime validation and the opaque output type from one definition.
   - Scope boundary: do not define any domain-state, API-body, event-envelope, or adapter schemas owned by #38.
3. **Public API shape** — exporting only a schema couples consumers to Zod operations; exporting only a parser hides useful schema composition.
   - Recommendation: export `correlationIdSchema`, inferred `CorrelationId`, `parseCorrelationId(input: unknown)`, and `generateCorrelationId()`. Keep failure details library-native internally unless a stable public error contract is explicitly required later.
4. **Inbound HTTP trust policy** — accept caller IDs, reject malformed caller IDs, or always generate server IDs.
   - Recommendation for #116: always generate at the API boundary. Do not enable Fastify `requestIdHeader`; it performs no validation. Treat acceptance of upstream IDs and proxy trust as a later explicit policy decision.
5. **HTTP propagation point and header** — per-route payload changes would duplicate infrastructure concerns.
   - Recommendation: configure `genReqId` in `buildApp()` with the contracts generator, then add a global infrastructure hook that writes `request.id` to the `x-correlation-id` response header. This covers `/health` without importing Fastify into application/domain code or changing an unrelated business payload.
6. **Error behavior** — the parser must reject malformed values, but #116 does not require the API to ingest caller-supplied correlation IDs.
   - Recommendation: prove parser rejection in contracts tests; do not invent an HTTP 400 error shape until inbound-header support is explicitly selected.

### Approaches

1. **Server-generated UUID v4 + Zod 4 + Fastify request lifecycle** — define one branded schema in contracts, generate an ID for every Fastify request, and echo it in `x-correlation-id`.
   - Pros: smallest acceptance-criteria-complete slice; one source of truth for type and validation; no caller-controlled logging identifier; no framework leakage; uses Node 24/Web Crypto capability.
   - Cons: does not preserve an upstream caller's correlation ID; requires a deliberate cross-runtime implementation detail for `randomUUID()` typing.
   - Effort: Low

2. **Validated inbound-or-generated UUID v4** — parse `x-correlation-id` when present, reject malformed values, otherwise generate one, and propagate the selected value.
   - Pros: supports service-to-service continuity immediately; exercises the parser at the HTTP boundary.
   - Cons: Fastify's built-in `requestIdHeader` is unsafe for this because it does not validate; a separate decoration/hook or carefully handled generator path is needed, plus explicit trust and error-response policy. This is broader than the acceptance criterion.
   - Effort: Medium

3. **Sortable ID format or handwritten validator** — use UUID v7/ULID, or avoid a validator dependency with a manual opaque-string parser.
   - Pros: sortable formats can aid storage/index locality; a handwritten parser can reduce runtime package weight.
   - Cons: ordering is not required; UUID v7/ULID may add generation dependencies or policy; a handwritten validator undermines coordination with #38 and duplicates schema infrastructure that the backlog already expects.
   - Effort: Medium

### Recommendation

Use approach 1 as the bounded #116 slice:

1. Adopt Zod 4 once, directly in `packages/contracts`, preferably through the workspace catalog so #38 has an explicit version to reuse.
2. Define a UUID-v4 branded schema and derive the public opaque `CorrelationId` type from it.
3. Export a thin parser and a Web-Crypto-backed generator from a dedicated correlation-ID module and the package barrel.
4. At `apps/api/src/infrastructure/http/build-app.ts`, use the generator as Fastify's `genReqId` and expose that same request-scoped ID through `x-correlation-id` on every response.
5. Keep all Fastify code in infrastructure. Application/domain code may carry `CorrelationId` as a contract type later, but this issue should not invent a use case or event envelope merely to demonstrate propagation.
6. Follow strict TDD: first add failing contracts tests and a failing Fastify injection test, then implement the minimum behavior. Add a focused boundary rule/test only if proposal scope still stays below the 400-line review budget.

This should fit comfortably within one review unit under the fixed 400 authored-line budget. The `auto-chain` strategy remains available if boundary fixtures or generated lockfile churn make the actual review unexpectedly large, but chaining is not currently recommended.

### External Research Lanes

No additional external research is required before proposal for the recommended bounded slice. Repository evidence establishes the architecture and dependency state, while current official Fastify documentation confirms that `request.id`/`genReqId` are the correct lifecycle seam and that `requestIdHeader` does not validate caller input. Current Zod 4 documentation confirms dedicated UUID-v4 validation, branding, and parse/safe-parse behavior.

Optional research should be offered only if the proposal expands beyond that slice:

- **Upstream identity and trust lane** — compare `x-correlation-id`, `x-request-id`, and W3C Trace Context; define proxy trust, overwrite/preserve rules, length limits, and rejection semantics before accepting caller IDs.
- **Validator portfolio lane** — benchmark Zod 4 against a smaller validator only if bundle size or cross-runtime constraints become an explicit #38 requirement. Do not delay #116 for an abstract library survey.
- **Cross-runtime generation lane** — verify the exact browser/edge targets only if `apps/web` must call the generator; the current acceptance criterion requires API generation only.

### Risks

- Enabling Fastify `requestIdHeader` would silently trust unvalidated caller input and violate the intended runtime-validation boundary.
- Treating the transitive Zod copy as usable would leave `packages/contracts` without a declared production dependency and could break under lockfile pruning.
- A root-level `node:crypto` import could make the contracts entry point hostile to browser consumers.
- Exporting Zod-specific error details as a stable API now could unnecessarily couple later consumers; keep the stable contract to success/failure parsing unless requirements say otherwise.
- Expanding into generic event envelopes, domain IDs, telemetry, tracing, or application-use-case plumbing would absorb #38/#98 scope and exceed this issue's purpose.
- The missing OpenSpec config/state is a workflow risk for later phases; native `sdd-new` should create or reconcile it rather than this executor inventing additional files.

### Ready for Proposal

Yes. The proposal can fix UUID v4, Zod 4, server-generated IDs, `x-correlation-id` response propagation, strict TDD, and framework-free boundaries as the default plan. It should return the inbound-header trust policy, cross-runtime generator typing, and any validator deviation as explicit decisions to the orchestrator rather than broadening #116. No external research gate is necessary unless the orchestrator chooses the inbound-ID or multi-validator expansion.
